# Bunvelope v2 — Domain Model

Normative. See `00-architecture.md` for the divergence convention.

One machine-readable schema (Zod, or JSON Schema + codegen) is the single source
for: TypeScript types, runtime validation, CLI flags, MCP `inputSchema`, and
migration scaffolding. Nothing below is hand-written twice.

---

## 1. Primitives

```ts
type Cents         = bigint & { readonly __unit: 'cents' }
type CentsPerMonth = bigint & { readonly __unit: 'cents/month' }
type CentsPerYear  = bigint & { readonly __unit: 'cents/year' }
type Units         = bigint & { readonly __unit: 'micro-units' }  // quantities, 10⁻⁶ scaled
type BasisPoints   = number                                        // integer, 10000 = 100%

type PlainDate = string & { readonly __brand: 'PlainDate' }   // 'YYYY-MM-DD'
type Instant   = string & { readonly __brand: 'Instant' }     // RFC3339 UTC
type Month     = string & { readonly __brand: 'Month' }       // 'YYYY-MM'

type EnvelopeId   = string & { readonly __brand: 'EnvelopeId' }
type AccountId    = string & { readonly __brand: 'AccountId' }
// … one branded id type per entity
```

**Where this document set says `Decimal`, it means `Units`** — a scaled
integer, never a float. Investment units are `bigint` micro-units (six decimal
places).

**`bigint` does not serialize to JSON.** At every persistence and transport
boundary a money or unit value is encoded as a **decimal string** and
re-branded on parse; the codec lives beside the schema, and a float reaching
an encoder is a programmer error (R3).

**Ids are ULIDs**, generated by the runtime. Sortable, collision-free,
device-safe, and opaque.

> ⚠️ **DIVERGES FROM v1** — v1 ids are human-readable slugs (`env-rent`) derived
> from `slugify(category-name)` with a collision suffix. Two consequences:
> renaming an envelope makes its id a lie, and **uniqueness is never checked at
> write time**. Duplicate `tx.id` from imports is a known real failure — a
> duplicate makes one row unreachable while the other answers for both, in every
> lookup the app builds. v2 ids are opaque and uniqueness is a schema constraint.

A separate human-facing `slug` may exist on envelopes and accounts for CLI
convenience (`--envelope groceries`); it is unique, mutable, and never used as a
foreign key.

## 2. Referential integrity

**Every reference below is a real foreign key**, validated at the write boundary,
with a declared delete rule.

> ⚠️ **DIVERGES FROM v1** — v1 has roughly sixteen foreign-key-shaped fields with
> **zero constraints and zero uniqueness checks**. The transaction validator
> requires exactly one field (`type`); a record consisting only of
> `{type: 'expense'}` — no id, no date, no amount, no account — writes cleanly
> through every validation layer the app has. Deleting an envelope leaves every
> reference dangling, and the app's answer is a `"(deleted)"` label at render
> time. The only referential check is advisory: it lights a status-bar badge and
> blocks nothing.

Delete rules:

| Reference | Rule |
|---|---|
| Posting → Envelope | `RESTRICT` — archive instead |
| Posting → Account | `RESTRICT` |
| PlanItem → Envelope / Account | `RESTRICT` |
| Occurrence → PlanItem | `skipped` records `CASCADE`; `RESTRICT` if `settled` (unsettle first). `pending` occurrences are virtual — nothing stored to cascade (§3.7) |
| Occurrence → Transaction (`settledBy`) | `CASCADE` — deleting the settling transaction deletes the occurrence record itself (§3.7) |
| TemplateLine → Envelope | `RESTRICT` |
| Settings → Envelope (`emergencyEnvelopeId`) | `SET NULL` |

**Parse, don't validate.** A negative expense magnitude, an unbalanced posting
set, a dangling reference and a malformed date are *unrepresentable*, not merely
invalid.

### 3.4 Transaction

```ts
type Transaction = {
  id:        TransactionId
  date:      PlainDate            // required
  payee:     string               // required; '' allowed, null is not
  note:      string               // required; '' allowed
  label:     TxLabel              // presentation only
  postings:  Posting[]            // ≥ 1, must balance
  status:    'posted' | 'pending' // required — absent is not a state
  cleared:   boolean              // reconciliation, orthogonal to status
  flagged:   boolean
  source:    Source               // provenance
  createdAt: Instant
  updatedAt: Instant
}

type TxLabel = 'expense' | 'income' | 'account-transfer' | 'envelope-transfer'
             | 'allocation' | 'adjustment' | 'investment' | 'debt-payment'

type Source  = { kind: 'manual' } | { kind: 'import', batchId: string }
             | { kind: 'occurrence', occurrenceId: OccurrenceId }
             | { kind: 'rollover', policy: string }
             | { kind: 'reconcile', accountId: AccountId }
             | { kind: 'ai', intent: string }
             | { kind: 'manual-correction' }
```

Four notes:

**`label` is presentation only.** It never affects arithmetic. All money movement
is in `postings`. The label exists so the UI can say "Expense" and the filter can
group — which is all the v1 `type` field was really doing once the sign rules
moved into postings.

**`status` is required.**

> ⚠️ **DIVERGES FROM v1** — in v1 an absent `status` means "posted", but the AI
> context builders filter on `status !== 'posted'` and therefore silently exclude
> **every manually entered transaction** from anomaly and health analysis. A
> convention that means one thing to the engine and the opposite to a consumer is
> a defect of optionality, not of either reader.

**`note` and `description` merge.** v1 carries two overlapping free-text fields.

**`source` replaces English payee text.** v1 writes `'Rollover: sweep to
unallocated'` and `'Template allocation'` into the persisted `payee`, which is
permanently untranslatable. In v2 the record carries structured provenance and
the adapter renders the label.

### 3.5 Posting — the single sign-bearing primitive

```ts
type Posting = {
  axis:     'account' | 'envelope'
  targetId: AccountId | EnvelopeId | null    // null on the envelope axis = unallocated
  amount:   Cents                            // signed; negative = out
  enteredAs?: { mode: 'set', target: Cents } // input echo only — see below
}
```

**`enteredAs` is an engine-blind input echo** (settled 2026-08-27). A fill
line entered as "set to X" is stored as the resolved delta
(`02-business-rules/02-postings-and-balances.md` §1.1) with this annotation
recording what the user typed. It is **never read by any engine path** — a
lint rule enforces that, and property A10 (`04-invariants-and-proof.md`)
asserts that mutating or stripping it changes no derived value. Adapters
render it strictly as past input ("entered as: set to €250"), because after
any edit to earlier history the target no longer corresponds to the delta.

**The balancing rule.** For every transaction:

```
Σ(account postings) − Σ(envelope postings) = Δunallocated
```

`unallocated` is *defined* as that difference, so the accounting identity holds
by construction rather than by check. A transaction whose postings cannot be
interpreted this way is rejected at the boundary. **`Σ(envelope postings)`
excludes null-target legs** — a posting with `targetId: null` *is* the
unallocated leg, not a summand of it; counting it on both sides of the
identity double-counts an envelope-transfer-to-unallocated
(`02-business-rules/02-postings-and-balances.md` §2.3).

Worked shapes:

| User event | Account postings | Envelope postings |
|---|---|---|
| Expense €50 | `checking −5000` | `groceries −5000` |
| Split expense €80 | `card −8000` | `food −6000`, `household −2000` |
| Income €2,000 | `checking +200000` | *(none — lands in unallocated)* |
| Account transfer €100 | `A −10000`, `B +10000` | *(none)* |
| Envelope transfer €30 | *(none)* | `dining −3000`, `fuel +3000` |
| Allocation (fill) | *(none)* | `rent +120000`, `food +40000`, … |
| Fill from new income | `checking −160000` | `rent +120000`, `food +40000` |
| Adjustment +€5 to an account | `checking +500` | *(none)* |

> ⚠️ **DIVERGES FROM v1** — v1 encodes the same information across eight type
> arms with per-type sign rules and overlapping optional fields, and re-implements
> the resulting math in five places. Its own engine source says: *"there are
> already too many copies of envelope/account sign logic in this codebase, and
> every one of them has drifted at least once."* The postings model has one
> implementation because there is only one shape.

**Investment postings** carry an extra optional group on the transaction, not on
the posting:

```ts
investment?: {
  symbol:     string         // uppercased ticker or ISIN
  direction:  'buy' | 'sell' | 'dividend' | 'adjust'
  units:      Decimal        // 6dp
  pricePerUnit: Cents        // 5dp equivalent, stored as minor units
  fee:        Cents
}
```

The fee's destination is a *rule*, not a field: it is absorbed by the investing
envelope, not the accounts. The general rule for every investment transaction is
`02-business-rules/02-postings-and-balances.md` §1; its application during
plan-item materialisation is `02-business-rules/01-calendar-and-scheduling.md` §3.

### 3.6 PlanItem

The annual plan line. May also drive recurrence.

| Field | Type | Req | Notes |
|---|---|---|---|
| `id` | PlanItemId | ✓ | |
| `envelopeId` | EnvelopeId | ✓ | **FK, required** |
| `accountId` | AccountId \| null | ✓ | Independent of `recurring` |
| `kind` | `'expense' \| 'income' \| 'investment'` | ✓ | |
| `description` | string | | |
| `amount` | Cents | ✓ | **Positive magnitude.** Direction comes from `kind`. |
| `schedule` | `MonthSchedule` | ✓ | See below |
| `paymentDay` | 0–31 | ✓ | `0` = no specific day |
| `dayType` | `'exact' \| 'next-work-day' \| 'prev-work-day'` | ✓ | |
| `buffer` | Cents | ✓ | Default `0` — a balance floor, **not** an addition to the fill |
| `include` | boolean | ✓ | |
| `includeInEmergency` | boolean | ✓ | |
| `recurring` | boolean | ✓ | Emits occurrences when true |
| `activeFrom` / `activeUntil` | PlainDate \| null | ✓ | |
| `investment` | `{ accountId, symbol, direction } \| null` | ✓ | |
| `stressCategory` | `'A' \| 'B' \| 'C' \| 'D' \| 'E' \| 'Z'` | ✓ | Default `'Z'` = never cut. See `02-business-rules/03-planning-and-policies.md` §12 |
| `stressCuts` | `{ [scenario in 'A'..'E']?: BasisPoints }` | | Per-scenario cut; an absent scenario cuts 0 |

```ts
type MonthSchedule = {
  [m in Month1..12]: { active: false } | { active: true, override: Cents | null }
}
```

> ⚠️ **DIVERGES FROM v1** — v1's `monthly_schedule` is a map whose values are
> **polymorphic**: `true` means "use the default amount", `false` means inactive,
> and a *number* means "override this month". A field that means two different
> kinds of thing depending on its runtime type is a parse hazard; v2 makes the
> discriminator explicit.
>
> v1 also stores `default_amount` **signed, negative for expenses** — the
> opposite convention to `tx.amount`. Two sign conventions in one budget. v2 uses
> a positive magnitude everywhere and derives direction from `kind`.
>
> v1 additionally carries `stress_cut_pct` (a legacy scalar) alongside
> `stress_cut_pcts` (its replacement map) indefinitely, and a legacy
> `template_id`. v2 carries only the per-scenario map (`stressCuts`) and drops
> both legacy fields. Stress modelling is **in scope** (decided 2026-08-27) —
> see `02-business-rules/03-planning-and-policies.md` §12.

### 3.7 Occurrence — new, and the highest-value change

```ts
type Occurrence = {
  id:         OccurrenceId
  planItemId: PlanItemId          // FK
  dueDate:    PlainDate           // the ADJUSTED payment date
  scheduleDate: PlainDate         // the RAW schedule date — owns window membership
  amount:     Cents
  status:     'pending' | 'settled' | 'skipped'
  settledBy:  TransactionId | null    // FK; non-null iff status === 'settled'
  skipReason: string | null
}
```

**`OccurrenceId` is deterministic — one of two exceptions to opaque ULIDs.** It
is derived from `(planItemId, scheduleDate)` (canonically the string
`${planItemId}:${scheduleDate}`, branded). Two devices materialising the same
due bill offline therefore mint the **same id**, and their ops converge onto
one record under the merge rules in `06-change-log.md` instead of
double-posting. An opaque id here would reintroduce the double-counting class
through sync — the exact family this entity exists to end. Template-fill and
rollover occurrences use the same construction with the template or envelope
id in the first position. **The other exception is the transaction id that
materialisation emits** — deterministic from the same occurrence id, for the
same reason (`02-business-rules/01-calendar-and-scheduling.md` §3; the first
decision under "Decided 2026-08-27 (architecture review)" in the README).

**Occurrences are virtual until they acquire independent state.** Generation
(`02-business-rules/01-calendar-and-scheduling.md` §2.2) is a **pure query**;
the projected `pending` occurrences a forecast shows are computed on demand,
never stored. A record is persisted only when an occurrence gains state the
schedule cannot re-derive: it is **settled** (materialised or hand-linked) or
**skipped**. A persisted record shadows the virtual occurrence with the same
id. Three consequences:

- Editing a plan item's schedule is **one op** — the pending horizon simply
  re-derives; there is no delete-and-recreate churn in the log.
- The op log carries no speculative rows, so sync traffic is proportional to
  what actually happened.
- `plan.item.delete`'s cascade touches only stored `skipped` records; in the
  common case there is nothing stored to cascade to.

**Both dates are stored** on the persisted record. Window ownership is decided
by `scheduleDate`; materialisation is gated on `dueDate`.

> ⚠️ **DIVERGES FROM v1** — v1 derives these and keeps neither. A bill on the
> 31st of a month whose 31st fell at a weekend belonged to **neither** of the two
> windows that could hold it and vanished from every forecast thereafter. The fix
> was to use the raw schedule date for ownership — a rule v1 must re-derive
> correctly in four separate places. Storing both dates makes it a field lookup.

`status: 'skipped'` replaces v1's `meta.scheduledTombstones` string array
entirely — a parallel record of "handled" stored in the metadata document with no
schema, no validation and no test coverage, which exists solely because deleting
a transaction in v1 deletes the only record that its occurrence was handled.

**Invariant:** `status === 'settled' ⟺ settledBy !== null`, and a transaction may
settle at most one occurrence.

**Deleting a transaction that settles an occurrence deletes the occurrence
record** (settled 2026-08-27; this is the `CASCADE` in §2, not the `SET NULL` a
plain foreign key would suggest). The occurrence reverts to virtual `pending`
and the bill re-materialises as due — deterministic ids (above) make this safe,
because the re-materialised occurrence carries the same id rather than a
duplicate. The invariant above therefore holds trivially: there is no
`settled`-with-`null-settledBy` state to reach, because the record that would
be in it stops existing. A user who deletes the payment but does not want the
bill to reappear skips the occurrence instead of deleting the transaction. The
op log is unaffected by this — the ops that created and deleted the record
still stand, so history and undo replay them (`06-change-log.md` §7).

### 3.8 Template

```ts
type Template = {
  id: TemplateId
  name: string
  description: string
  lines: TemplateLine[]
  schedule: TemplateSchedule | null
  sourceEnvelopeId: EnvelopeId | null    // fund from an envelope rather than unallocated
}

type TemplateLine = {
  envelopeId: EnvelopeId
  mode: 'add' | 'set'
  rule: { kind: 'fixed', amount: Cents }
       | { kind: 'percent-of-plan', basisPoints: number }
       | { kind: 'goal-required' }   // the envelope's goal monthlyRequired at generation time
}
```

One shape. A template may mix fixed, percent and goal lines. A
`goal-required` line resolves to the envelope's current
`goalProgress.monthlyRequired`
(`02-business-rules/03-planning-and-policies.md` §10) and to `null` — dropped
— when the envelope has no goal or the goal is reached, so goal funding stands
down by itself the month the goal completes.

> ⚠️ **DIVERGES FROM v1** — v1 has two species (`manual` / `dynamic`) with
> separate editors, separate math and a one-way "you cannot convert between types
> later" warning.

`TemplateSchedule` is the only sub-object v1 validates properly, and for a stated
reason worth preserving: *a malformed schedule that reaches the walker moves
money on the wrong day — or every day.* v2 applies that standard everywhere.

### 3.9 Holding

**Derived, never stored** — computed from investment postings at average cost.
An override is a separate entity, so a hand-typed position never silently
replaces derived truth without a record:

```ts
type HoldingOverride = {
  accountId: AccountId
  symbol: string
  units: Decimal
  costBasis: Cents
  reason: string
  setAt: Instant
}
```

Prices live in their own collection — and it is **append-only history**, not
latest-per-symbol: each record is a price point `{symbol, price, asOf}`, the
current price is the point with the greatest `asOf`, and the history is what
powers the net-worth-over-time report
(`02-business-rules/04-forecast-and-history.md` §7). This is a one-line schema
difference now and a painful retrofit later.

### 3.10 Settings

```ts
type Settings = {
  schemaVersion: number
  name:          string
  currency:      string          // ISO 4217
  locale:        string
  calendarId:    string          // banking calendar — see 02-business-rules/01 §1
  emergency:     { envelopeId: EnvelopeId | null, months: number, creditMode: 'all' | 'flagged' }
  closedMonths:  Month[]         // months closed by the review — see 03-api-surface.md §2.14
}
```

Plus one more collection, `bankingCalendars`, holding user-defined or overridden
calendars. Built-in calendars are data files shipped with the app; a record here
shadows a built-in of the same id. See `02-business-rules/01-calendar-and-scheduling.md`
§1 for the rule algebra.

**That is the whole of it.**

> ⚠️ **DIVERGES FROM v1** — v1's `budget-meta.json` is a junk drawer whose only
> validated field is `schemaVersion`. It holds AI consent state (which then
> travels with an export, so re-importing carries someone else's consent), the
> scheduled-tombstone array, investment prices, holding overrides, payee rules,
> and `manualRows` — a second hidden transaction ledger. In v2: consent is
> per-user runtime state, tombstones are occurrence status, and everything
> investment-related is a real collection.

## 5. Display order

Array order is display order, as in v1 — but expressed as an explicit `sortKey`
field rather than as array position.

> ⚠️ **DIVERGES FROM v1** — v1 relies on the position of an element within the
> persisted array, which makes reordering an implicit consequence of any code
> path that rebuilds or re-sorts the collection, with nothing to detect it. With
> an op log and per-entity ops, array position is not even well-defined.
